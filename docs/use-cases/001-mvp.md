# Definición del MVP de Friggy

## Objetivo y viabilidad

El MVP debe permitir completar el siguiente recorrido de principio a fin:

> Crear ingredientes, crear una receta con sus pasos y asignarla a las comidas de una semana.

Su desarrollo es viable en dos semanas de dedicación completa, estimadas en 60–80 horas, siempre que se mantenga el alcance definido en este documento. El repositorio parte únicamente de documentación, por lo que la estimación incluye la creación de la solución, la persistencia, la interfaz y las pruebas.

Quedan fuera del MVP la inteligencia artificial, las imágenes, la información nutricional, el frigorífico virtual, la lista de la compra, la autenticación y el despliegue público.

## Implementación del MVP

* Crear una única solución .NET 10 con ASP.NET Core, Blazor Web App con interactividad en servidor, Minimal APIs y Entity Framework Core.
* Utilizar PostgreSQL como base de datos, ejecutado localmente en un contenedor mediante Docker Compose y con un volumen persistente.
* Gestionar el esquema mediante migraciones versionadas de Entity Framework Core. La cadena de conexión se proporcionará a la aplicación mediante `ConnectionStrings__FriggyDb` y no se incluirán credenciales reales en el repositorio.
* Organizar los endpoints por funcionalidad mediante métodos de extensión, manteniendo `Program.cs` reducido.
* Compartir servicios de aplicación entre la interfaz Blazor y las Minimal APIs para evitar duplicar reglas de negocio.
* Crear pantallas para ingredientes, listado y edición de recetas, detalle de receta y calendario semanal. Las pantallas incluirán estados vacíos, validación visible, confirmación al borrar y mensajes de error comprensibles.
* Proporcionar datos de ejemplo opcionales y documentación para iniciar la aplicación localmente.

### Modelo de datos

* `Ingredient`: identificador y nombre único.
* `Recipe`: nombre, tiempo estimado y tipos de comida recomendados.
* `RecipeIngredient`: receta, ingrediente, cantidad decimal positiva, tipo de unidad y orden.
* `UnitType`: nombre y símbolo únicos. Se incluirán inicialmente gramo, kilogramo, mililitro, litro, unidad, cucharadita y cucharada.
* `RecipeStep`: receta, posición, descripción y tiempo opcional.
* `RecipeTag`: nombre único. Su relación con `Recipe` será de muchos a muchos mediante una tabla intermedia.
* `MealType`: nombre y orden; desayuno, comida y cena se crearán como datos iniciales.
* `WeeklyPlan`: nombre, lunes de inicio y descripción opcional. Su fecha final se calcula como la fecha inicial más seis días.
* `MealPlanEntry`: plan semanal, fecha, tipo de comida y receta. Solo podrá existir una entrada por combinación de plan, fecha y tipo de comida.

`UnitType` y `RecipeTag` serán tablas administradas por la aplicación, no enumeraciones del código. Esto permitirá ampliar sus valores sin modificar ni recompilar el dominio.

### API prevista

Las Minimal APIs expondrán operaciones CRUD mediante las rutas `/api/ingredients`, `/api/recipes`, `/api/recipe-tags`, `/api/unit-types`, `/api/meal-types` y `/api/weekly-plans`. Las recetas devolverán sus ingredientes, etiquetas y pasos ordenados; los planes semanales devolverán sus siete días y las asignaciones correspondientes.

### Automatización local

El proyecto incluirá scripts PowerShell idempotentes:

* `scripts/setup.ps1` comprobará la disponibilidad de .NET 10, Docker y Docker Compose; creará `.env` a partir de `.env.example` cuando no exista; iniciará el servicio de PostgreSQL; esperará a que su comprobación de salud sea satisfactoria; restaurará las dependencias y aplicará las migraciones.
* `scripts/start.ps1` comprobará o iniciará el contenedor de PostgreSQL y ejecutará API y Web con el perfil de desarrollo; Web consumirá API exclusivamente por HTTP.
* `scripts/quality-gate.ps1` restaurará, compilará, verificará formato, ejecutará las cinco suites y auditará vulnerabilidades NuGet.

Los scripts terminarán con un código distinto de cero y un mensaje accionable cuando falte un requisito o no se pueda iniciar PostgreSQL. No sobrescribirán un archivo `.env` existente ni eliminarán el volumen de datos.

## Calendario de diez días laborables

1. Crear la solución, Docker Compose, PostgreSQL, scripts PowerShell, migración inicial y estructura de pruebas.
2. Implementar ingredientes, tipos de unidad, etiquetas y tipos de comida.
3. Implementar el modelo y la API de recetas.
4. Construir el formulario de recetas e ingredientes.
5. Incorporar pasos ordenados, etiquetas y validaciones.
6. Implementar el modelo y la API de planificación semanal.
7. Construir el calendario semanal y la asignación de recetas.
8. Completar edición, borrado, estados vacíos y manejo de errores.
9. Añadir pruebas automatizadas, datos de ejemplo y correcciones.
10. Realizar una sesión piloto local, actualizar la documentación y reservar margen para incidencias.

Si al terminar el quinto día no funciona la creación completa de recetas, se recortará primero la administración de tipos de comida. Desayuno, comida y cena permanecerán entonces como datos iniciales no editables.

## Pruebas y criterios de aceptación

* Ejecutar `scripts/setup.ps1` dos veces consecutivas sin perder datos ni producir errores.
* Ejecutar `scripts/start.ps1` con PostgreSQL detenido y comprobar que inicia tanto la base de datos como la aplicación.
* Crear, editar y borrar ingredientes, etiquetas y tipos de unidad sin admitir nombres vacíos o duplicados.
* Crear una receta con varios ingredientes, unidades, etiquetas y pasos, conservando correctamente su orden.
* Rechazar cantidades y tiempos negativos.
* Crear una semana a partir de un lunes y mostrar exactamente siete días.
* Asignar, sustituir y retirar una receta de cada comida.
* Impedir referencias inválidas y gestionar el borrado de registros que estén en uso.
* Reiniciar la aplicación y el contenedor de PostgreSQL sin perder datos.
* Completar el recorrido principal desde la interfaz, sin utilizar OpenAPI ni modificar directamente la base de datos.
* Ejecutar pruebas unitarias de las reglas de dominio y pruebas de integración de los endpoints contra PostgreSQL.

El piloto técnico local del 10 de agosto de 2026 verificó este recorrido con setup idempotente, API/Web disponibles y 15/15 escenarios E2E correctos. La sesión con una persona real queda como piloto guiado posterior; su registro técnico está en el [cierre ejecutable de la Fase 6](../../plans/completed/implementation/06-stabilization-and-pilot-implementation.md#67--piloto-y-cierre--completada).

## Supuestos

* La aplicación será monousuario y se ejecutará localmente durante sesiones piloto guiadas.
* Docker Desktop, Docker Compose y .NET 10 son requisitos del entorno de desarrollo.
* La interfaz será funcional y clara, sin exigir el acabado visual de un producto comercial.
* La fase posterior al MVP incorporará inventario por lotes con caducidad, historial de movimientos, raciones por asignación semanal y consumo al completar una comida. No realizará conversiones entre unidades; la lista de la compra permanecerá para una fase posterior independiente.
