# Definición histórica del MVP de Friggy

> **Estado:** histórico · **MVP completado:** 10 de agosto de 2026 · **Última revisión:** 20 de agosto de 2026

Este documento conserva el objetivo y resultado del primer MVP. No es la fuente del comportamiento actual; consulta [Funcionalidades actuales](../product/current-capabilities.md), [Estado y hoja de ruta](../product/roadmap.md) y las [guías de usuario](../user-guide/getting-started.md).

## Objetivo original

El MVP debía completar de principio a fin este recorrido:

> Crear ingredientes, crear una receta con sus pasos y asignarla a las comidas de una semana.

La estimación original fue de diez días laborables y 60–80 horas. Quedaron fuera de esa primera entrega la inteligencia artificial, las imágenes, la información nutricional, el inventario doméstico, la lista de la compra, la autenticación y el despliegue público.

## Resultado del MVP

El piloto técnico verificó:

* Catálogos editables de ingredientes, unidades, etiquetas y tipos de comida.
* Recetas con ingredientes, cantidades, unidades, etiquetas, tipos de comida y pasos ordenados.
* Planes de siete días iniciados en lunes y asignación de recetas.
* Web Blazor consumiendo la API exclusivamente por HTTP.
* PostgreSQL persistente mediante Docker Compose y migraciones versionadas.
* Preparación idempotente, reinicio sin pérdida de datos y recorrido E2E completo.

El cierre ejecutable se conserva en la [Fase 6](../../plans/completed/implementation/06-stabilization-and-pilot-implementation.md#67--piloto-y-cierre--completada).

## Evolución posterior

Después del MVP se entregaron capacidades que este documento situaba originalmente fuera de alcance:

* Inventario por lotes con cantidad, unidad, caducidad e historial de movimientos.
* Raciones por asignación semanal y cálculo de cantidades faltantes.
* Finalización de comidas con consumo transaccional de lotes.
* Huecos de comida por día, orden, horario e inicio de preparación derivado.
* Comidas omitidas con motivo y alternativa opcional.
* Asociación de líneas de ingredientes con pasos de receta.
* Sistema visual responsive, accesible y protegido por regresión visual.

Las fases 7 a 11 y su gate final están documentadas en [plans](../../plans/README.md). La autenticación, la lista de la compra, las conversiones, las imágenes, la información nutricional, la inteligencia artificial y el despliegue público siguen fuera de la versión actual.

## Arquitectura resultante

La solución utiliza .NET 10, ASP.NET Core, Minimal APIs, Blazor con interactividad en servidor, Entity Framework Core y PostgreSQL:

```text
Friggy.Domain <- Friggy.Application <- Friggy.Infrastructure <- Friggy.Api
                         ^
                         |
              Friggy.Web (contratos)

Friggy.Web -> HTTP -> Friggy.Api -> Application -> Infrastructure -> PostgreSQL
```

Web comparte contratos inmutables de Application, pero no ejecuta sus servicios ni accede a Infrastructure. API es el composition root. Consulta [Arquitectura para contribuidores](../development/architecture.md).

## Modelo actual respecto al MVP

El modelo original incluía `Ingredient`, `UnitType`, `RecipeTag`, `MealType`, `Recipe`, `RecipeIngredient`, `RecipeStep`, `WeeklyPlan` y `MealPlanEntry`. La evolución añadió:

* `RecipeStepIngredientLink` para asociar líneas concretas con pasos.
* `MealPlanSlot` para configurar cada día de forma independiente.
* Raciones, horario y estados planificado, omitido o completado.
* `InventoryLot` e `InventoryMovement` para existencias e historial.

Los catálogos permanecen como tablas administradas por la aplicación, no como enumeraciones del código.

## Automatización vigente

La previsión inicial de crear `.env` no se implementó. El flujo actual utiliza valores locales versionados y permite sobrescribir la conexión mediante entorno:

* `scripts/setup.ps1` valida .NET, Docker, Node.js y pnpm; instala dependencias; inicia PostgreSQL; restaura .NET; aplica migraciones e instala Chromium.
* `scripts/start.ps1` inicia PostgreSQL, API y Web sin duplicar procesos disponibles.
* `scripts/stop.ps1` detiene los tres servicios sin eliminar el volumen.
* `scripts/test.ps1` compila Release y ejecuta las cinco suites.
* `scripts/quality-gate.ps1` añade formato y auditorías de vulnerabilidades.

La conexión de ejecución se llama `ConnectionStrings:Friggy`, o `ConnectionStrings__Friggy` como variable de entorno. Las herramientas de diseño aceptan `FRIGGY_CONNECTION_STRING`. Consulta [Entorno local](../development/environment.md) y [Persistencia y migraciones](../development/database.md).

## Criterios que continúan vigentes

* No admitir nombres vacíos o duplicados en catálogos.
* Rechazar cantidades o tiempos inválidos.
* Proteger referencias utilizadas y operaciones incompatibles con el estado actual.
* Conservar datos tras reiniciar aplicación y contenedor.
* Probar reglas de dominio y casos de uso en su capa correspondiente.
* Probar API, migraciones y persistencia con PostgreSQL real.
* Completar recorridos críticos desde Web sin modificar directamente la base de datos.

La estrategia vigente se documenta en [ADR 004](../adr/004-tdd-and-testing-strategy.md) y [Estrategia y ejecución de pruebas](../development/testing.md).
